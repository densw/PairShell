# 临时设备码：开源调研与实现边界

## 复用依据

- Magic Wormhole 使用 PAKE 让双方以人可转述的短码建立端到端秘密，服务端负责 rendezvous，不能把短码直接当作普通加密口令。[项目安全说明](https://magic-wormhole.readthedocs.io/en/latest/welcome.html)
- [wormhole-william](https://github.com/psanford/wormhole-william) 为 Go 的 Magic Wormhole 实现；采用完整库还需要兼容的独立 mailbox 服务。本项目保留已有协调服务和 SSH/Pion，不额外部署另一套文件传输基础设施。
- [schollz/pake](https://github.com/schollz/pake) 供 croc 使用，提供 PAKE 与有序参与者身份绑定。本实现固定 `github.com/schollz/pake/v3 v3.2.1`、P-256；调用其现成实现，不自行实现曲线或 PAKE。该库不宣称完全符合 RFC 9382，也不能把复用等同于本产品已经通过独立安全审查。

## 默认交互

客户点击开始等待，显示 `1234-5678-9012` 风格的一次性配对码。前六位是公开邮箱定位符，后六位是密码学随机生成的 PAKE 秘密。连字符只用于显示分组。商家输入完整配对码后，双方在当前会话中分别核对对方通过独立可信渠道读出的校验码。商家端确认和客户本机授权均完成后，才能建立执行通道。每次新会话均需重新核对。

密码部分为六位均匀随机十进制，约 19.9 位熵。定位符不计入秘密熵。正常服务端每个信箱最多三次认领，生成配对码的一端也独立限制每个码最多三次不同的 PAKE 证明。失败后使用新的 PAKE 实例，服务端重置无法恢复本地额度。三次都失败后码失效，需要用户生成新码。

当前生成并接受完整 12 位码，允许连字符、空白和全角数字等输入格式归一化。密码部分保持六位随机十进制，有效期、严格限次、PAKE 和本机授权均必需。

## 流程

1. 管理员显式启用公开设备配对后，客户调用 `/v1/device/create` 注册有界、五分钟有效的匿名信箱，发送公开 PAKE 初始消息。该步骤没有执行权限，也不需要部署令牌。
2. 商家以六位定位符短期认领信箱。服务端发放接收凭据，仅保存 SHA-256 摘要。
3. 双方使用 PAKE 的有序角色、服务器来源和应用域标识导出密钥，并通过 HKDF 将密钥绑定邮箱 ID 与定位符。客户设备核对商家的密钥证明后，由信箱所有者授权签发一次性建房许可。
4. 一次性许可绑定认领来源，只在本次短期限内有效。匿名创建受每来源上限和全局配额限制，同时给管理员保留房间容量。可操作两端的匿名用户仍可申请资源。
5. 商家以 AES-GCM 加密原有完整邀请，绑定服务器、邮箱 ID 和定位符作为附加认证数据。邀请的配对秘密不会以明文交给服务器。
6. 客户解密并验证邀请仍属于所选服务器，返回密钥确认。两端完成邀请领取、临时密钥证明和认证信令后，在本机显示会话校验码。双方通过独立可信渠道核对完整校验码。桌面点击确认，CLI 输入对方读出的完整校验码。成功核对且客户本机授权后，才建立固定两端会话密钥的 SSH 通道。

服务端只处理有界的公开 PAKE 消息与密文，普通错误不包含完整码、邀请或凭据。握手解析边界也容纳依赖对畸形公开值的 panic，统一返回不可用错误。

## 自建服务器准入模式

`server.Config.PublicDevicePairing` 默认为 `false`；私有实例保持部署令牌准入，匿名 `/v1/device/create` 返回 403。既有商家通过部署令牌创建邀请、再发布配对码的兼容入口继续工作。

官方公共服务或接受匿名资源消耗的自建实例需显式传入 `pairshelld -device-pairing`，对应 `PublicDevicePairing: true`。该开关独立于 `-public-create`。任何网络访问者都能在限额内申请临时信箱，获得建房许可需要信箱所有者授权。执行仍须通过客户本机确认、会话撤销、审计及 SSH 密钥固定。

不要为减少一步输入而在未显式开启该模式的私有实例上静默放开准入，也不要把管理员部署令牌打包进客户端。

## 接口

`paircode.Listen(ctx, base, client)` 返回客户配对码以及一次结果通道；结果只有解密并验证过的邀请或错误。

`remote.ConnectCode(ctx, base, code, deployToken, client)` 使用一次性许可（当 deployToken 为空）建立商家会话，随后仍须调用现有 `Connect`，客户仍须授权。`paircode.Publish/Receive` 和 `Merchant.PairCode` 保留商家先发送码的兼容方向。

## 已验证与限制

自动化覆盖：正确码、错误秘密、领取重放、并发二十次领取只成功一次、长度/容量限制、许可过期和单次消费、拒绝无凭据全局建房、畸形 PAKE 值，以及完整 TLS → 客户设备码 → PAKE → Pion → SSH 链路。

默认每来源可同时占用四个匿名信箱和四个匿名房间。服务器仍能阻断连接和观察元数据。即使中继绕过自己的限次，同一个码的生成端仍会限制它能够验证的不同证明数。六位秘密可能被猜中，使用不可信中继时仍须通过独立渠道核对双方。客户端遇到旧服务器时不会降级上传明文邀请。[三方安全协助](trust.md)
